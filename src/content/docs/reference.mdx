## Server commands

| Command | What it does |
|---|---|
| `telesphorepo-server serve` | Runs the server. `telesphorepo-server` with no command does the same. |
| `telesphorepo-server dev` | Runs a local server with demo repositories and demo data. Add `--empty` for empty repositories. |
| `telesphorepo-server user add NAME [--admin]` | Creates a user. It asks for the password. |
| `telesphorepo-server user passwd NAME` | Sets a new password and signs the user out everywhere. |
| `telesphorepo-server user reset-2fa NAME` | Removes every second factor of the user. |
| `telesphorepo-server version` | Prints the version. |
| `telesphorepo-server help [command]` | Shows the help of a command. |

In the container, put `docker exec -it telesphorepo /telesphorepo-server` before the command. The `user` commands change the database in `TR_DATA_DIR`.

## CLI commands

The server serves the Telesphorepo CLI of its own version. Install it with `curl -fsSL https://repo.example.com/install.sh | sh`, or on Windows with `irm https://repo.example.com/install.ps1 | iex`. See [Install the CLI](/install-cli/).

| Command | What it does |
|---|---|
| `telesphorepo setup LINK` | Sets up the project of this folder from the setup line of the **Publish to this repository** tab. It approves the computer and writes `telesphorepo.toml`. For a Docker repository, it adds the credential helper to the Docker config. |
| `telesphorepo publish [FILE...]` | Publishes the project of this folder: Gradle, Maven, npm, Python, Cargo, .NET or a Helm chart. For a raw or Debian repository, it uploads each FILE. For Python and .NET, FILE names wheels, sdists or `.nupkg` files to upload with no build. |
| `telesphorepo login SERVER` | Approves this computer for a server, with no project. |
| `telesphorepo logout [SERVER]` | Revokes the approval of this computer, and removes its files and its Docker helper entries. |
| `telesphorepo status` | Shows the approvals of this computer and the project of this folder. It shows no secret. |
| `telesphorepo update [SERVER]` | Installs the CLI of the server. A newer CLI stays, because it works with an older server. |
| `telesphorepo version` | Prints the version. |
| `telesphorepo help [command]` | Shows the help of a command, with examples. |

The CLI keeps the key of each approved computer in `~/.telesphorepo/<server>/device.json`. Only you can read the file.

### telesphorepo.toml

| Key | What it sets |
|---|---|
| `server` | The address of the server |
| `repo` | The repository |
| `kind` | `maven` or `gradle`, when the folder holds both |
| `path` | The folder in a raw repository |
| `dist`, `component` | The distribution and the component of a Debian repository |

### CI variables

| Variable | What it sets |
|---|---|
| `OIDC_TOKEN` | The identity token of a Jenkins job. Its audience must be the address of the server. GitHub Actions needs no variable: the job needs `id-token: write`. |
| `TELESPHOREPO_SERVER` | The server of the Docker credential helper in CI |

## Environment variables

No variable is required.

| Variable | Default | What it sets |
|---|---|---|
| `TR_DATA_DIR` | `./data`, `/data` in the image | The folder for the database, the files and the master key |
| `TR_LISTEN` | `:8080` | The listen address |
| `TR_MASTER_KEY` | a file in the data folder | The key that encrypts secret settings: 32 bytes, base64 |
| `TR_BOOTSTRAP_ADMIN_USER`, `TR_BOOTSTRAP_ADMIN_PASSWORD` | `admin` and a random password | The first admin. The server reads them only while it has no users |

A change to these variables needs a restart.

## Settings

Change settings in the web UI, on the pages **General**, **Storage**, **Sign-in options** and **Network and proxy** under **Settings**. A change applies at once.

You can also force any setting from the environment. The name is `TR_` plus the key in capitals, with `_` for each `.`. For example, `s3.bucket` becomes `TR_S3_BUCKET`. The web UI then shows the setting as read only.

## Repository addresses

The examples use the server `https://repo.example.com` and a repository named `REPO`.

| Format | Kinds | Address for clients |
|---|---|---|
| Maven / Gradle | hosted, proxy, group | `https://repo.example.com/maven/REPO` |
| npm | hosted, proxy, group | `https://repo.example.com/npm/REPO/` |
| Python (PyPI) | hosted, proxy, group | `https://repo.example.com/pypi/REPO/simple/` to install, `https://repo.example.com/pypi/REPO/` to upload |
| Cargo (Rust) | hosted, proxy, group | `sparse+https://repo.example.com/cargo/REPO/index/` |
| NuGet | hosted, proxy, group | `https://repo.example.com/nuget/REPO/index.json` |
| Docker | hosted, proxy, group | `repo.example.com/REPO/IMAGE:TAG`, at the root of the host |
| Debian (apt) | hosted, proxy | `https://repo.example.com/debian/REPO` |
| Raw files | hosted | `https://repo.example.com/raw/REPO` |

A proxy keeps a copy of each file that people download from its remote. A group serves its members in order, and takes no uploads. In a group of npm, Python, Cargo or NuGet repositories, the first member that has a package name owns it: the group serves every version of that name from that member only, so a public package cannot shadow a private one. A Maven group merges `maven-metadata.xml` over its members, so the versions of all members show. A Docker group serves each file from the first member that has it, and lists the tags of all members.

## HTTP API

The web UI uses a JSON API under `/api/`. The full list of routes is in [SPEC.md](https://github.com/Telesphorepo/Telesphorepo/blob/main/SPEC.md#http-surface) in the source repository.

`GET /healthz` answers `ok` when the server runs. Use it for health checks.
