## Serve over HTTPS

The server speaks plain HTTP on port 8080. Put a reverse proxy in front of it for HTTPS. [Caddy](https://caddyserver.com) gets a certificate for you.

<Steps>

1. Save this as `Caddyfile` and start Caddy:

   ```text title="Caddyfile"
   repo.example.com {
       reverse_proxy localhost:8080
   }
   ```

2. Open the server once through Caddy.

3. Trust the proxy. Open **Settings** › **Network and proxy**. Under **Detected proxies**, click **Trust** on the row of Caddy. Click **Save**, then **Save changes**.

4. Open **Settings** › **General**. Set **Public base URL** to `https://repo.example.com`, and click **Save**.

</Steps>

Step 3 lets the server see the real address of each client. Rate limits and the audit log need it.

<details>
<summary>Cloudflare in front</summary>

On the **Network and proxy** page, under **Where your proxy is**, tick **Cloudflare**. If Caddy sits between Cloudflare and the server, also tick **Other addresses** and add the address of Caddy.

</details>

<details>
<summary>Other proxies</summary>

- Let the proxy accept request bodies up to the **Max upload size** of the server (**Settings** › **General**). The default is 2 GiB. Some proxies stop at 1 MiB.
- Without a proxy, on plain HTTP and a host that is not `localhost`, the browser drops the session cookie. Start the server with `-e TR_COOKIE_SECURE=false`. Maven also refuses plain HTTP, and pip, Yarn, dotnet and Docker each need a setting for it, so use HTTPS for real use.

</details>

## Push large images

Behind Cloudflare (Free and Pro plans), each image layer must be under 100 MB. Pulls have no limit. Not behind Cloudflare? You have nothing to do.

To push larger layers, let the layers skip Cloudflare. People still push to the main address. The server tells the client to send the layers to a second address: the upload address. Nobody changes a command.

<Aside type="caution">
This makes the IP address of your server public.
</Aside>

<Steps>

1. In Cloudflare, add a second name for your server, for example `upload.example.com`. Make the record **DNS only**. Serve it over HTTPS, as in the steps above.

2. Open the port of that name in the firewall of your server, for the computers that push.

3. Open **Settings** › **General**. Under **Docker**, set **Docker upload address** to `https://upload.example.com`. Turn on **Expose the origin IP for Docker uploads**. Click **Save**.

</Steps>

Pulls, logins and the credential helper keep the main address.

ORAS and Helm 4 send layers only to the address in the command. Push with them to the upload address:

```sh
helm push mychart-0.1.0.tgz oci://upload.example.com/docker
oras push upload.example.com/docker/team/art:1.0 file.txt
```
<details>
<summary>HTTP/2 and TLS</summary>

The server speaks HTTP/1.1 and HTTP/2. Behind a reverse proxy, the server also takes HTTP/2 without TLS, for a proxy that sends it. A proxy that sends HTTP/1.1 works too, so you need no change.

To let the server do TLS itself, set `TR_TLS_CERT_FILE` and `TR_TLS_KEY_FILE` to a certificate and a key (PEM files). Both are needed. The server loads a renewed certificate without a restart. Turning TLS on or off needs a restart.

</details>

## Store files in S3

The server keeps files on its local disk by default. To use a bucket, such as Cloudflare R2, AWS S3 or SeaweedFS:

<Steps>

1. Create the bucket and an access key that can read, write and delete in it.
2. Open **Settings** › **Storage**. Under **Storage type**, choose **An S3 bucket**. Enter the **Address**, the **Region**, the **Bucket**, the **Access key ID** and the **Secret access key**. Leave the **Address** empty for AWS S3.
3. Click **Test connection**. The server writes, reads and deletes one test file.
4. Click **Save** and confirm. If the server has files, it copies them to the bucket in the background. Downloads and uploads keep working during the copy.

</Steps>

<details>
<summary>Values for R2 and SeaweedFS</summary>

<Tabs>
<TabItem label="Cloudflare R2">

| Setting | Value |
|---|---|
| Address | `https://<account>.r2.cloudflarestorage.com` |
| Region | leave it empty, or `auto` |
| Path-style addresses | off |

</TabItem>
<TabItem label="SeaweedFS">

| Setting | Value |
|---|---|
| Address | `http://seaweedfs:8333` |
| Region | any name, for example `us-east-1` |
| Path-style addresses | on |

</TabItem>
</Tabs>

By default, a download from S3 goes straight from the bucket to the client. If clients cannot reach the bucket, turn off **Download from the bucket**.

The old files stay where they were. Delete them yourself when the new storage works.

With an address and no region, the server signs requests for the region `auto`, which R2 needs. AWS needs a real region, for example `us-east-1`.

</details>

## Keep the master key safe

The server encrypts secret settings with a master key. By default it writes the key to `master.key` in the data volume. Without the key, the server cannot read the S3 secret, the single sign-on secret, the signing keys and the authenticator apps.

To keep the key out of the volume, create one before the first start and pass it in:

```sh
openssl rand -base64 32
```

```sh
docker run -d --name telesphorepo -p 8080:8080 -v telesphorepo-data:/data \
  -e TR_MASTER_KEY="$(cat /run/secrets/tr_master_key)" \
  ghcr.io/telesphorepo/telesphorepo:latest
```

Do not change `TR_MASTER_KEY` later.

## Run with Docker Compose

This one file runs the server, Caddy for HTTPS, and a volume for backups.

<Steps>

1. Save these two files in a folder of their own. Put your address in place of `repo.example.com` in both.

   ```yaml title="compose.yaml"
   services:
     telesphorepo:
       image: ghcr.io/telesphorepo/telesphorepo:latest
       restart: unless-stopped
       environment:
         TR_BASE_URL: https://repo.example.com
         TR_BACKUP_DIR: /backups
       volumes:
         - data:/data
         - backups:/backups
       depends_on:
         backups-owner:
           condition: service_completed_successfully

     # The server runs as user 65532. A new volume belongs to root, so this gives the backups volume to the server once.
     backups-owner:
       image: alpine:3
       command: chown 65532:65532 /backups
       volumes:
         - backups:/backups

     caddy:
       image: caddy:2
       restart: unless-stopped
       ports:
         - "80:80"
         - "443:443"
         - "443:443/udp"
       volumes:
         - ./Caddyfile:/etc/caddy/Caddyfile:ro
         - caddy-data:/data
         - caddy-config:/config

   volumes:
     data:
     backups:
     caddy-data:
     caddy-config:
   ```

   ```text title="Caddyfile"
   repo.example.com {
       reverse_proxy telesphorepo:8080
   }
   ```

2. Point the DNS name at the host, then start everything:

   ```sh
   docker compose up -d
   ```

3. Copy the admin password from the log, and sign in at `https://repo.example.com`:

   ```sh
   docker compose logs telesphorepo
   ```

4. Trust Caddy: open **Settings** › **Network and proxy**, click **Trust** on the row of Caddy under **Detected proxies**, then **Save** and **Save changes**.

</Steps>

`TR_BASE_URL` and `TR_BACKUP_DIR` set the public address and the backup folder from the file, so the UI shows them read-only. Leave them out to set them in **Settings** instead. To keep the master key out of the data volume, add `TR_MASTER_KEY` from a secret (see below).

## Back up

The server backs itself up. Set a folder under **Settings** › **Server** › **Backups** (or `TR_BACKUP_DIR`, as in the Compose file above). It then writes a backup every 24 hours and keeps the newest 7; change both on the same page, or click **Back up now**.

A backup is a folder with a copy of the database, the master key and, with local disk storage, the stored files. Files in an S3 bucket stay in the bucket, so back up the bucket too, with its versioning or replication. A master key in `TR_MASTER_KEY` is not written into the backup; keep it with the backups.

The backup volume must belong to the server's user, 65532. Give a new volume to it once:

```sh
docker run --rm -v telesphorepo-backups:/b alpine chown 65532:65532 /b
```

<details>
<summary>Back up from the command line</summary>

This works while the server runs:

```sh
docker run --rm -v telesphorepo-data:/data -v telesphorepo-backups:/backups \
  ghcr.io/telesphorepo/telesphorepo:latest backup /backups
```

</details>

## Restore

Restore a backup folder into an empty volume, then start the server on that volume:

```sh
docker run --rm -v telesphorepo-backups:/backups -v telesphorepo-restored:/data \
  ghcr.io/telesphorepo/telesphorepo:latest restore /backups/20261020T201500.123Z
```

The restore checks the database against its checksum, refuses a volume that is not empty, and says whether the backup is from the same version of Telesphorepo as the image.

## Upgrade

<Steps>

1. Back up: click **Back up now** under **Settings** › **Server** › **Backups**.
2. Pull the new image and start a new container on the same volume:

   <Tabs>
   <TabItem label="Docker Compose">

   ```sh
   docker compose pull
   docker compose up -d
   ```

   </TabItem>
   <TabItem label="Docker">

   ```sh
   docker pull ghcr.io/telesphorepo/telesphorepo:latest
   docker stop telesphorepo
   docker rm telesphorepo
   docker run -d --name telesphorepo -p 8080:8080 -v telesphorepo-data:/data ghcr.io/telesphorepo/telesphorepo:latest
   ```

   </TabItem>
   </Tabs>

3. Check that it runs:

   ```sh
   curl https://repo.example.com/healthz
   ```

   The answer is `ok`.

</Steps>

Pass the same `-e` variables as before. On its first start, a new version updates the database to its own structure, one step at a time, and the log names each step. The server refuses to start on a database from a newer version. To go back to an older version, restore the backup you made in step 1.

<Aside>
All settings live in the database. Change them in **Settings**. Each change applies at once, with no restart. See [Reference](/reference/) for the environment variables.
</Aside>
