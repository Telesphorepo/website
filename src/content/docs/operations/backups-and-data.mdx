Everything Telesphorepo needs to run is in the data directory (`TR_DATA_DIR`) plus, if you use S3, one bucket. In the container image the data directory is the volume `/data`. This page lists what is there and how to back it up.

## What is in the data directory

| Path | Contents |
|---|---|
| `telesphorepo.db` | The SQLite database in WAL mode. Users, repos, permissions, the asset index, settings, sessions, publish records and Nexus sources |
| `telesphorepo.db-wal`, `telesphorepo.db-shm` | The write-ahead log and shared memory of the database. They exist while the server runs |
| `master.key` | The master key (base64, mode 0600). The server creates it on first start, unless `TR_MASTER_KEY` is set |
| `blobs/` | The files of every repo, when storage is `fs` (or the directory in `fs.root`) |
| `tmp/` | The upload spool. You do not need to back it up |

With storage `s3`, the blobs are in the bucket and `blobs/` stays empty.

## What to back up

You need all three parts, taken close together in time:

1. The **database**. It says which files exist, who can read them and how the server is set up.
2. The **blobs**: the `blobs/` directory, or the bucket.
3. The **master key**.

<Aside type="caution">
The database and the blobs must match. A database that lists a file the blobs do not hold gives errors on download. Take the database backup first and the blobs after it, or stop the server for both.
</Aside>

## Back up the database

The database uses WAL mode. The newest writes can be in `telesphorepo.db-wal` and not yet in `telesphorepo.db`. Do not copy only `telesphorepo.db` from a running server.

<Tabs>
  <TabItem label="Stop the server">
    The simplest safe backup. Stop the server, copy the data directory, and start the server again.

    ```sh
    docker stop telesphorepo
    docker run --rm -v telesphorepo-data:/data -v "$PWD":/backup alpine \
      tar czf /backup/telesphorepo-$(date +%F).tar.gz -C /data .
    docker start telesphorepo
    ```

    A clean shutdown merges the WAL into the database. The archive then holds the database, the master key and the local blobs together.
  </TabItem>
  <TabItem label="SQLite backup">
    Use the SQLite online backup while the server runs. It gives a consistent copy, including the WAL content. You need the `sqlite3` command-line tool on the machine that can read the data directory. The container image does not include it.

    ```sh
    sqlite3 /path/to/data/telesphorepo.db ".backup '/backups/telesphorepo.db'"
    ```

    Or write a compacted copy:

    ```sh
    sqlite3 /path/to/data/telesphorepo.db "VACUUM INTO '/backups/telesphorepo.db'"
    ```

    Then copy `master.key` and the blobs separately.
  </TabItem>
</Tabs>

Test a restore on another machine from time to time. Start the server on the restored directory and sign in.

## Back up the blobs

- **Filesystem.** Copy the `blobs/` directory (or `fs.root`) with a tool of your choice, such as `rsync`. Blobs are never edited in place: the server writes a temporary file and renames it. A copy of a running server is therefore safe for files that already exist.
- **S3.** Use the bucket features of your provider: versioning, replication or a scheduled copy to a second bucket. Telesphorepo does not back up the bucket.

## The master key

The master key encrypts the secret settings: the S3 secret key, the OIDC client secret and the Debian signing key. The server derives the encryption key from it with HKDF-SHA256 and uses AES-256-GCM.

There are two ways to hold it:

- **In the data directory.** The server writes `master.key` on first start. Your data backup then includes it.
- **In the environment.** Set `TR_MASTER_KEY` to a base64 value of 32 bytes. This keeps the key off the volume. Store it in your secret manager and back it up there.

<Aside type="caution" title="Lost master key">
Without the master key, the server cannot decrypt the secret settings. You must enter them again: the S3 secret, the OIDC client secret and so on. Keep the key in a different place from the database backup, but keep it.
</Aside>

If you move the data to a new server, move the master key with it, or set the same `TR_MASTER_KEY`.

## Gotchas

- Do not restore an old database on top of a newer set of blobs, or the other way round, without checking that downloads work.
- A database that is newer than the server binary is refused at start. See [Upgrading](/operations/upgrading/).
- Take a backup before a [storage move](/operations/moving-storage/), a [Nexus cut-over](/operations/nexus-migration/) or an upgrade.
